# DIBK design system

Adapts **Designsystemet** (Digdir, the Norwegian government design system) into a
DIBK-branded design system for DIBK's apps: a theme, brand components, and brand icons,
all wrapping `@digdir/designsystemet-react` so apps install one package.

## Workspace

pnpm workspace (`packages/*`, `apps/*`):

- `packages/designsystem` (`dibk-designsystemet`) - the library. Re-exports **all** of
  `@digdir/designsystemet-react` (v1.15) and adds DIBK components. Ships the generated
  theme + base + override CSS. Dual ESM + CJS, built with tsup. React, react-dom,
  `@digdir/designsystemet-{react,css}` and `@fontsource/poppins` are peer dependencies,
  so the consuming app owns exactly one copy of each. Three JS entries: the barrel
  (`.`), the layout primitives (`./layout`) and the brand icons (`./icons`).
- `apps/demo` (`dibk-designsystemet-demo`) - runnable app (Vite). `#/` is an
  information page about the design system; the examples are `#/nettsted` and
  `#/komponenter`. All example content is invented.

## Commands

```sh
corepack enable pnpm        # pnpm is NOT on PATH after a container restart - run this first
pnpm install                # if it complains, use: CI=true pnpm install --no-frozen-lockfile
pnpm build                  # icons codegen + tsup + generated theme/styles/fonts CSS
pnpm theme                  # regenerate dist/theme.css only (after changing the brand color)
pnpm icons                  # regenerate src/icons/ from svg/ only
pnpm demo                   # demo app dev server
```

Filtered builds: `pnpm --filter <name> build`. The demo aliases each JS entry to its
**source** so editing components hot-reloads without rebuilding the library. The aliases
are anchored regexes (`/^dibk-designsystemet$/` and one per subpath): a bare string alias
also swallows the subpaths, and anchoring leaves the CSS subpaths to resolve through the
real workspace link. The CSS entries are generated into `dist/`, so run `pnpm build` at
least once.

## DIBK design language

- **Brand navy `#003045`** (the accent).
- **`border-radius: 0`** everywhere (the signature trait - everything square).
- **Pale surface colors** (brand-specific, not derived from the accent):
  blue `#ebf4fa`, green `#f1fae3`, orange `#faf0de`, grey `#f4f4f4`. These (plus the
  brand ink) live as `--dibk-*` custom properties in `src/base.css`
  (`--dibk-surface-{blue,blue-hover,green,orange,grey,pink}`, `--dibk-color-ink`,
  `--dibk-color-meta`, `--dibk-color-hairline`) - the
  single source of truth. Components reference the tokens, not raw hex. The navy
  accent comes from the generated theme as `--ds-color-accent-base-default`.
- Ink `#202020`; warm grey `#6b6560` for meta text.
- **Font: Poppins** (`@fontsource/poppins`, OFL-1.1). Static font - import weights 300-700.
- Two link styles: navigation links = ink, medium weight, no underline (underline on
  hover); prose/inline links = navy, bold, underlined.

## How theming works

A theme is just a CSS file of `--ds-*` custom properties. `packages/designsystem/scripts/build-theme.mjs`
calls `formatThemeCSS` from `@digdir/designsystemet/tokens` to generate `dist/theme.css`
from the brand color + radius + font. Don't hand-edit `dist/theme.css`; change the script
and re-run `pnpm theme`. Designsystemet's own `@digdir/designsystemet-theme` package is
deprecated - don't add it.

App CSS imports. `dibk-designsystemet` is the single seam: consumers import only its
entries, never `@digdir/*` directly. Two explicit imports, and the JS entries carry no
CSS at all, because a JS file that imports CSS cannot be loaded by Node and would break
SSR and the CJS build.
```ts
import "dibk-designsystemet/fonts.css";  // Poppins @font-face
import "dibk-designsystemet/styles.css"; // DS component CSS + theme + base + overrides + layout
```
`dist/styles.css` is generated by `scripts/build-styles-entry.mjs` and `@import`s, in
cascade order, `@digdir/designsystemet-css` (by bare specifier, so it resolves from the
*consumer's* node_modules at their build time), then `theme.css`, `index.css` and
`layout.css`. Designsystemet is a peer dependency, so inlining a copy of its CSS here
would freeze one version while the consumer floats the React package. `fonts.css` is
separate so an app can supply its own typeface by importing `styles.css` alone.
`theme.css`, `index.css` and `layout.css` stay exported for consumers that need to
compose a different cascade.

## Tailoring Designsystemet to DIBK: `src/overrides.css`

This is the key pattern. To restyle a stock Designsystemet component to the DIBK look,
add a rule to `packages/designsystem/src/overrides.css`. Designsystemet's CSS lives in
`@layer ds`, so **plain unlayered rules win without needing high specificity or
`!important`**. Already overridden there:

- **Global font-weight reduction** - remaps `--ds-font-weight-regular/medium/semibold`
  to 300/400/500 (Poppins renders heavy). This is the single weight lever; custom
  components reference these tokens, not magic numbers.
- **Letter-spacing** - tightened (body -0.01em, headings -0.02em; no single DS token).
- **Alert** - border removed (DIBK callouts are flat pale panels).
- **Card** - all cards are flat, no border; background via `data-dibk-color="blue|green|orange|grey|pink"`
  (white default). Uses a custom attribute, NOT DS `data-color`, because `data-color`
  cascades the whole color family (would turn buttons/headings blue/green).
- **Details (accordion)** - pale-blue panels, navy header, chevron on the right, gap
  between items.

`src/base.css` applies `--ds-font-family` to `body` (DS only fonts its own components,
so plain text would otherwise fall back to serif). Both base.css and overrides.css are
imported by `src/index.ts`; esbuild strips those imports from the JS output and bundles
them, with every component's CSS, into `dist/index.css`, which `dist/styles.css` pulls in.

## Custom components

`Dibk` prefix, in `packages/designsystem/src/components/*`. Each has `index.tsx` +
`Component.css` (imported by the component; esbuild bundles it). Components style via
the `--dibk-*` and `--ds-*` tokens (never raw hex). List: `DibkAppShell`, `DibkHeader`,
`DibkFooter`, `DibkMegaMenu`, `DibkMenuSection`, `DibkSearch`, `DibkIconLinkList`,
`DibkSectionHeader`, `DibkFeedbackWidget`, `DibkLogo`, `DibkAccountMenu`,
`DibkMenuLogin`, `DibkCopyButton`/`DibkCopyIconButton`, `DibkCodeBlock`. `DibkAppShell` is the page frame (header + mega-menu + content container +
footer); its content sits in the `--dibk-container-max` / `--dibk-container-pad` container
(base.css), which the header and footer also use so all three align edge-to-edge.

Conventions every custom component follows:

- **Compose, don't reimplement.** Where Designsystemet has the primitive, wrap it and
  restyle via the override pattern - don't hand-roll. Buttons are DS `Button` (Header
  toggles + MegaMenu close = `variant="tertiary"`; FeedbackWidget Ja/Nei =
  `primary`/`secondary`), the MegaMenu search field is DS `Search` (`Search.Input` +
  `Search.Clear` + `Search.Button`) flattened to the DIBK underline look.
- **Forward props + ref.** Each `extends ComponentPropsWithoutRef<...>` for its root
  element, merges `className`, spreads `...rest`, and is wrapped in `forwardRef`, so
  consumers can pass `className`/`style`/`data-*`/`aria-*` and grab the node.
- Shared decorative glyphs live in `src/components/icons.tsx` (internal, not exported).

**Layout primitives** (`src/components/Layout/`) are the exception to the `Dibk` prefix:
`Stack`, `Cluster`, `Sidebar`, `Grid` are unprefixed (layout is generic) and use a neutral
`l-*` CSS namespace, not `dibk-`. They are published from `src/layout.ts` as the
`./layout` subpath, NOT from the main barrel: the barrel star-exports
`@digdir/designsystemet-react`, and a name reachable through two star-exports is dropped
from both, so an upstream `Grid` or `Stack` would silently break every consumer. Token-driven `gap` (`xs|sm|md|lg` -> `--ds-size-2/3/5/8`),
polymorphic `as`, zero runtime. Responsiveness is intrinsic (Sidebar/Grid reflow with no
media query); components that restyle by their own width use a per-component container query
(`container: <name> / inline-size` on a frame the component renders, queried by its content).
See the "Layout primitives" section in `packages/designsystem/README.md`. Don't add a
class-grid framework.

## Icons (`dibk-designsystemet/icons`)

Raw SVGs in `packages/designsystem/svg/` are the source of truth. `pnpm icons` (runs on
build) regenerates `src/icons/` React components: camelCases kebab attrs, namespaces
`<clipPath>` ids, converts inline `style` strings to JSX objects. It wipes `src/icons/`
first, which is why the SVGs live at the package root rather than inside it. Icons are
**multi-color brand illustrations** (navy/orange/light-blue/green) - they do NOT follow
`currentColor`. Use a named import (`IconNabovarsel`) or the `dibkIcons` name→component
registry.

## Conventions / gotchas

- Custom-component weights use the `--ds-font-weight-*` tokens (one lever), not numbers.
- Designsystemet `data-size` on Headings wins over a CSS `font-size` class (it's applied
  at higher priority); set size via `data-size`, and force a weight via the `style` prop
  if needed.
- `@fontsource-variable/*` registers families with a " Variable" suffix (e.g. "Inter
  Variable"); static fonts (Poppins) use the plain name.
- Published to **public npmjs** as `dibk-designsystemet`, unscoped, `UNLICENSED`.
- Never publish without explicit approval from the user for that specific release.
